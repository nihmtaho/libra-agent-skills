# Release v0.1.2 with the four Define skills

## Problem
The 17-skill set exists only in the working tree. `skills-lock.json` still
described v0.1.1 with 14 skills including `write-spec`, `docs/PROJECT.md` Next
item 1 says to install v0.1.1, and there is no changelog. A user upgrading would
get the set without the four Define skills, and nothing tells them that
`write-spec` is gone and their old symlink now dangles.

## Use cases
1. A user runs the documented install command and gets 17 skills, none named
   `write-spec`.
2. A user upgrading from v0.1.1 reads the changelog, sees `write-spec` removed,
   and knows to run the uninstall loop before reinstalling.
3. A maintainer tags v0.1.2 and the state file points at a version that exists.

## Structure
- `CHANGELOG.md` — new at the repo root. Added, Changed, Removed for `0.1.2`.
- `docs/PROJECT.md` — one Features row for this release, and `## Next` item 1
  moved to v0.1.2.
- `docs/specs/release-v0-1-2.md` and `docs/tasks/release-v0-1-2.md` — this spec
  and its plan.
- `README.md` — only if the install command must name the tag.
- `evals/run.sh` and `evals/README.md` — contract evals for the four Define
  skills, and the live rubric a human runs.
- `skills-lock.json` — removed. It recorded this repo's own v0.1.1 install, and
  its hashes come from the skills CLI, so a hand-edited copy would be a claim
  nobody checked. A project gets its own lock when it installs.

## Code style
- The repo's voice: short declarative sentences, no marketing, no emoji.
- A changelog entry names the skill, never the file that changed.
- Release notes are the `0.1.2` section of the changelog, copied, not rewritten.

## Test plan
- `bash scripts/test.sh` — five lines green: `all checks passed`,
  `fixtures passed`, `routing passed`, `evals passed`, `install tests passed`.
- `./install.sh --to agents,claude --dest <throwaway>` — 17 links, no
  `write-spec`, and the installed `check-docs.sh` runs.
- Failure path: installing over a v0.1.1 tree that still holds a `write-spec`
  symlink must leave that symlink alone and the changelog must say how to remove
  it. `install.sh` never deletes what it did not create.

## Acceptance criteria
- [ ] `bash scripts/test.sh` exits 0 and prints the five green lines.
- [ ] `ls skills | wc -l` prints 17 and `skills-lock.json` no longer exists.
- [ ] A fresh `./install.sh` into an empty directory links 17 skills and no
      `write-spec`.
- [ ] `git tag -l v0.1.2` prints `v0.1.2`, and `git show v0.1.2 --stat` includes
      the four new skill directories.
- [ ] `CHANGELOG.md` has `## [0.1.2]` listing the four skills as added and
      `write-spec` as removed.

## Out of scope
- Rewriting the dated design doc and the old plans: they record what was decided
  then, and rewriting them loses that.
- README translations, CI, landing page, the separation evaluation: the deferred
  list, not a release.
- Hand-computing lock hashes. The file is generated by the skills CLI against a
  tag, never edited.
